# Invoke configured child Agents through an internal MCP tool

Each callable child Agent Definition generates one internal MCP tool with a definition-specific description, bounded business input, and exact result contract. A parent discovers only the generated children in its pinned Definition allowlist and cannot submit an arbitrary Definition identity. All generated tools share a thin adapter over Nano's existing Delegation Kernel and PostgreSQL runtime; child Agents are not separate MCP Servers.

Definition identity and integer version form the exact `identity@version` reference. Tool names are derived, not authored: `delegate.<identity>.v<version>`. Startup validates MCP name and length constraints, rejects collisions, verifies the child's task and result contracts, and confirms that both the parent and child Executors permit the relationship. Configuration can narrow those registered ceilings but cannot create authority.

Sprint 10 retains the existing depth-one topology: one parent may create one child in total, the child cannot delegate, and there is no sibling, fan-out, recursion, join, quorum, or free-form Agent conversation. This ADR standardizes how a configured child is invoked; it does not widen the graph.

Delegation uses a standard synchronous MCP `tools/call` whose operation is to accept durable child work, not to wait for that work's business result. One PostgreSQL transaction resolves or creates by stable `action_id`, records the accepted parent Proposal, creates the child Agent Run and Job, and moves the parent to `waiting` without a Lease. The returned scheduling receipt is consumed by the Controller as a control signal and is never appended to model context as the Action Result. Nano does not claim that receipt is an SEP-2663 Task.

Child terminalization requeues an eligible parent through PostgreSQL. The resumed parent resolves the Delegation and immutable Agent Result directly from the authoritative runtime store, then appends the validated Result reference as the original Action Result. It never retains a Lease or polls MCP while waiting. Notifications are advisory; normal Job polling recovers a missed notification.

A successful child stores one immutable, contract-versioned Agent Result with canonical JSON, SHA-256, and byte size. Delegation, parent Checkpoint, and Trace carry only its reference and integrity metadata. The child receives a bounded server-built context manifest; full parent context, hidden reasoning, raw Provider envelopes, and model-supplied authority never cross the boundary.

The first deployment keeps MCP Host and Nano Tools MCP Server in the Worker process over the official SDK's in-memory transport. Conformance covers locked protocol negotiation, scoped discovery, metadata authority, standard `tools/call`, scheduling receipt normalization, and the durable suspend/resume boundary. Remote transport remains deferred until another real Host requires it.

We rejected direct child-Run creation in individual Executors because it hard-codes Agent identities and duplicates durable lifecycle behavior. We also rejected one MCP Server per Agent and MCP Sampling because both introduce a second orchestration authority without improving the bounded runtime. We rejected making SEP-2663 a prerequisite for internal configured children because Nano already owns both endpoints and the durable PostgreSQL lifecycle; protocol Tasks solve remote-client interoperability, not Nano's parent suspension correctness.

Implementation note (2026-07-28): official Go SDK `v1.7.0-pre.3` provides everything required by this ADR's standard MCP boundary. SEP-2663 or A2A may later be added as adapters if Nano exposes long-running work to generic remote MCP clients or independently deployed Agents; neither changes the internal Delegation truth.
