# Use Kafka and ClickHouse for event-shaped observability

Nano Notebook will use Kafka as the durable decoupling boundary and ClickHouse as the query store for structured application logs, Operational Trace records, and Durable Agent Trace records. These signals retain separate topics, schemas, consumers, reliability policies, and query models rather than becoming one generic log stream. Metrics remain on the Prometheus scrape and remote-write path, encrypted Replay content remains in object storage, and PostgreSQL remains authoritative for product state.

This replaces the earlier assumption that Durable Agent Trace delivery can rely only on bounded producer memory and direct Collector HTTP delivery. Kafka is introduced for durable buffering, independent consumer scaling, replay, and fan-out; it is not adopted as a universal transport for every kind of system data.

Observability availability never determines product success: an accepted Run, Checkpoint, publication, or other product transaction does not fail because Kafka, a consumer, or ClickHouse is unavailable. Structured application logs and Operational Trace records remain best-effort signals. Accepted Durable Agent Trace records instead require eventual at-least-once delivery without silent permanent loss; downstream processing must therefore tolerate duplicate, delayed, and out-of-order records. Data-governance control commands such as deletion remain durable and independently observable.

Operational and Durable Agent Trace messages are partitioned by `trace_id` for locality, but Kafka partition order is not a correctness contract: independent producers can still observe and publish causal operations in different orders. Every Durable Agent Trace record has a stable identity and canonical content hash. Repeated identity with the same hash is an idempotent replay; repeated identity with a different hash is quarantined as a conflict. Agent Trace Processor projections converge as records arrive and expose unresolved structure as incomplete instead of fabricating missing history. Structured application logs have no cross-record ordering contract.

Kafka is a finite-retention delivery and replay buffer, not the long-term observability authority. Within the configured data-retention window, immutable ClickHouse raw tables are authoritative for structured logs, Operational Trace spans, and Durable Agent Trace records. Query-oriented summaries, timelines, and Token, Cost, latency, and error aggregates are rebuildable ClickHouse projections derived from those raw tables. Encrypted Replay content remains authoritative in object storage; ClickHouse stores only its bounded metadata and references.

Structured application logs and Operational Trace spans use OpenTelemetry signal schemas and semantic conventions. Durable Agent Trace records retain a separate, strongly versioned Nano domain contract for stable identity, canonical hash, Run and Attempt lifecycle, Checkpoint and Action relationships, Delegation, Token and Cost analysis, and Replay references. The contracts correlate through explicit identifiers such as `trace_id`, `span_id`, `run_id`, service, environment, tenant boundary, timestamp, and schema version; an OpenTelemetry mirror is never the Durable Agent Trace authority.

The Agent Trace Processor is the horizontally scalable storage Consumer Group for Durable Agent Trace messages. Its instances share partitions within that group and persist the raw authority plus query projections idempotently. New independent capabilities such as anomaly detection, cost analysis, evaluation, or archival use separate Consumer Groups so they can scale, fail, and replay without changing producers or blocking Trace storage.

Every Kafka message uses a registered, strongly typed, versioned schema envelope. Additive optional changes must remain backward compatible; field removal, type changes, and semantic reinterpretation require a new major contract and, when coexistence would be ambiguous, a new topic. Producers and CI verify compatibility before publication, rolling consumers understand at least the current and previous supported versions, and an unknown major version is quarantined rather than guessed. Durable Agent Trace canonical hashes are computed under an explicit schema version.

Consumer failures are classified by recoverability. Transient infrastructure failures such as ClickHouse unavailability do not advance the source offset and instead surface as retry and consumer-lag signals. Permanently invalid records, unsupported major schemas, and identity conflicts advance only after an immutable diagnostic envelope has been durably written to a quarantine topic; quarantine is queryable, alerted, and replayable rather than a silent sink. Missing causal peers and other out-of-order dependencies are valid incomplete Trace state, not poison messages: their raw records are retained and projections converge when dependencies arrive.

Retention is signal-specific and environment-configurable rather than inherited indefinitely from product rows. The production baseline is seven days for Kafka replay, thirty days for structured logs, fourteen days for Operational Traces, ninety days for Durable Agent Traces, thirty days for quarantined records, seven days for encrypted Replay, and fifteen days for Prometheus metrics. An authorized product deletion overrides every observational retention window: affected data becomes unavailable to queries immediately and proceeds to physical removal independently of its remaining TTL.

Deletion remains a separate durable control plane rather than an ordinary Trace event. The product transaction records the authoritative purge intent in PostgreSQL; Kafka delivers the command to the Agent Trace Processor, which establishes a Tombstone before asynchronously removing ClickHouse raw records, projections, and encrypted Replay objects. Queries reject a Tombstoned Trace immediately, and late, replayed, or disaster-recovered data cannot recreate it. Purge completes only after every owned store acknowledges physical removal, while the Tombstone survives all relevant Kafka, late-arrival, and backup-recovery windows.

Product state remains strongly consistent while observability queries are explicitly eventually consistent. The production freshness objective is searchable data within five seconds at p95 and thirty seconds at p99 after Kafka acceptance. Agent success never waits for this projection, Dashboard responses never synthesize a second Trace from product PostgreSQL, and query state distinguishes active, complete, incomplete, delayed, and Tombstoned data. Consumer lag beyond the freshness objective is an observable incident rather than evidence that a Run produced no Trace.

Cutover requires a reproducible performance and correctness evaluation, not an assumed technology benefit. The current direct HTTP and Observability PostgreSQL architecture is frozen and measured first as the authoritative baseline. A Kafka-to-PostgreSQL stage isolates transport decoupling from storage effects, and the final Kafka-to-ClickHouse stage isolates storage and query effects. The authoritative runs use two isolated Google Compute Engine C4A ARM64 VMs in one `asia-southeast1` zone and private network: a `c4a-standard-8` System Under Test and an independent `c4a-standard-4` load generator. The SUT starts calibration with a separate 100 GiB Hyperdisk Balanced data volume provisioned at 12,000 IOPS and 500 MiB/s; database, broker, and benchmark data never fall back to the boot disk. A production-shaped calibration fixture measures PostgreSQL, Kafka, and ClickHouse storage amplification, after which the volume may grow to twice the largest measured stable footprint. The resulting capacity is frozen before the Stage A baseline and remains unchanged through A/B/C. The headline end-to-end workload is a versioned Agent Run suite that emits correlated structured logs, Operational Traces, and Durable Agent Traces. Its business-capacity denominator is sustainable root Agent Runs per second, so delegated child Runs cannot inflate the headline; every result also reports total Agent Runs per second, Records per second, bytes per second, child Runs per root Run, and Records per root Run to expose internal amplification. Source Processing is a separate secondary workload because mixing it into the headline would make the business unit and bottleneck depend on an arbitrary traffic ratio. Raw Record injection is diagnostic component evidence only. Every comparison holds the SUT CPU, memory, total data-disk budget, dataset, durability, and workload constant and records the exact zone, machine image, kernel, container images, and provisioned disk parameters. The primary capacity measure is maximum sustainable throughput while freshness, producer latency, query latency, error rate, lag, and resource SLOs remain satisfied; burst-only numbers are not accepted as migration evidence.

The versioned headline suite begins with `agent-run-reference-v1`, a deterministic cycle of 100 root Agent Runs: 50 direct-answer Runs, 30 single-Action Runs, 10 two-Action Runs, 5 Delegation Runs, and 5 retry/recovery Runs. This is a controlled reference mix, not a claim about observed production traffic. Each scenario also runs in isolation as a sensitivity test so a favorable or unfavorable mixed-workload ratio cannot hide the limiting path. A future mix derived from production telemetry receives a new version and never rewrites prior benchmark meaning.

Dataset sizing is measurement-gated. `calibration-100k` contains 100,000 fully materialized root Agent Runs and establishes records per root, bytes per root, raw/projection/index amplification, and compression for every A/B/C stage. `primary-1m` contains 1,000,000 fully materialized root Runs and is the authoritative throughput and query dataset. The retention-scale target is 5,000,000 fully materialized root Runs; if calibration predicts that this target cannot leave at least 50% free space on the final permitted data volume, the target becomes 2,000,000 instead. The selected retention cardinality and final volume size are frozen before Stage A and remain identical through A/B/C. The legacy 100,000-summary plus one 256-Span fixture remains a compatibility gate only and cannot support migration or resume performance claims.

Capacity discovery uses an open-loop root-Run arrival rate rather than closed-loop client concurrency. Starting at one root Run per second, the load generator doubles the offered rate until the first SLO failure, then refines the interval between the last passing and first failing rates in approximately 25% steps. Each level has a two-minute warmup and ten-minute measurement window. The boundary passing rate and first failing rate each run three independent repetitions; a boundary classification requires the same outcome in at least two repetitions. Observed concurrency is reported but does not throttle offered demand. Closed-loop concurrency tests remain secondary latency diagnostics and cannot determine the headline sustainable rate.

The report distinguishes a performance knee from saturation. The knee is the first passing rate at which a critical p95/p99 latency or lag measurement degrades by more than 50% from the previous passing level and repeats on confirmation. Saturation is the first rate that violates any hard gate in at least two of three repetitions; maximum sustainable throughput is the highest passing rate below it. A valid level schedules at least 99.9% of target arrivals without load-generator saturation; loses, drops, or unexpectedly quarantines zero valid records; keeps transient pipeline error rate below 0.1%; keeps record-created-to-stage-acceptance latency at or below one second p95 and five seconds p99; keeps record-created-to-searchable freshness at or below five seconds p95 and thirty seconds p99; has no positive normal-backlog or Kafka-lag trend during the final five measurement minutes and drains to its starting level within two minutes; satisfies every frozen query SLO; and incurs no process restart, OOM, or sustained swapping while memory remains below 90% and data-disk free space remains at least 40%. CPU and I/O utilization identify the limiting resource but do not fail an otherwise passing level by themselves.

Query evaluation uses two versioned corpora. `trace-product-query-v1` represents the current Dashboard contract: 25% recent first-page lists, 20% combined time/status/model/Agent filters, 10% deep cursor pages, 15% exact Trace/workload/Run/Chat identity lookups, 20% ordinary direct/tool Trace details, and 10% Delegation/retry detail. It participates in the headline mixed-load SLO. `trace-analytics-query-v1` is a separate new-capability suite over one-hour, twenty-four-hour, seven-day, and full-retention windows, with identical PostgreSQL and ClickHouse result semantics for Token/Cost aggregates, error rates and latency percentiles, and Retry/Action/Delegation counts grouped by bounded model, Agent, status, and time dimensions. Analytical results are reported separately and cannot change the headline product-query weighting.

The decision-facing report remains deliberately compact even though the underlying experiment is reproducible in detail. It reports, for stages A/B/C, maximum sustainable root Agent Runs/s with Records/s and MiB/s, the repeatable performance-knee and saturation loads with the limiting component, product and analytical query p95/p99 latency, Kafka outage-buffer and backlog-recovery behavior including record loss, and retained-storage bytes per root Run. Harness mechanics, sample sizing, ramp refinement, and repetition details remain internal evidence unless they change cost, architecture, or the validity of a resume claim.
