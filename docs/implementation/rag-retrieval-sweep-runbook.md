# RAG Retrieval Sweep runbook

## Purpose

`rag-eval sweep` runs the production retrieval pipeline (dense embedding, BM25,
RRF fusion, evidence reload, rerank) without the Agent LLM loop, then reports
Recall/MRR and per-stage latency for query-time parameter combinations.

The current suite is `evals/rag/retrieval-sweep-v1.json`: 50 English MS MARCO
cases and 50 Chinese DuReader-retrieval cases. Every case is one real passage
admitted through the normal Source ingestion pipeline and labeled with the
nano-notebook Evidence Unit IDs produced by the active Index Version.

`prepare_dataset.py` now also samples a FiQA (English, financial-domain) and a
CmedqaRetrieval (Chinese, medical-domain) vertical alongside MS MARCO/DuReader,
plus random unrelated distractor passages per dataset (see
`docs/superpowers/specs/2026-08-05-rerank-relevance-gate-design.md`), so the
rerank relevance score has a real irrelevant-candidate population to compare
against. The "Results" section below still reflects the original two-dataset,
no-distractor run; it needs a rerun against the extended suite before the
`rerank_relevance_threshold` in `evals/rag/pinned-config-v1.json` can be set to
anything other than its current disabled value of `0`.

## Data

Sample JSONL is generated by:

```sh
python3 -m venv /tmp/nano-rag-eval-venv
/tmp/nano-rag-eval-venv/bin/pip install -r scripts/rag-eval/requirements.txt
/tmp/nano-rag-eval-venv/bin/python scripts/rag-eval/prepare_dataset.py
```

The sampler writes to gitignored `evals/rag/.dataset-cache/`:

- `msmarco-passage-v1.jsonl`
- `beir-fiqa-v1.jsonl`
- `dureader-retrieval-dev.jsonl`
- `cmedqa-retrieval-v1.jsonl`
- `samples-combined.jsonl` (all four, for a single `build-suite` pass)
- `dataset-manifest.json`

Every row in these files carries `is_distractor`. `rag-eval ingest-samples`
admits distractor rows as ordinary Sources exactly like relevant-passage rows;
`rag-eval build-suite` admits them into the retrieval candidate pool but never
adds them to a Case's `expected_evidence_sets` — they exist only to give the
rerank score a genuinely irrelevant candidate to score. `--distractor-count`
(default 40 per sub-dataset) controls how many are sampled; they are drawn
randomly from each sub-dataset's own corpus, excluding whatever was sampled as
relevant, so they stay unrelated rather than adversarial hard negatives.

MS MARCO and FiQA are restricted to non-commercial research. DuReader-retrieval
and CmedqaRetrieval are mirrored on HuggingFace for academic use.

Authority:

- MS MARCO Passage Ranking comes from Microsoft's official MS MARCO dataset and
  is one of the standard passage-ranking benchmarks used by TREC Deep Learning.
  Source: <https://microsoft.github.io/msmarco/>.
- FiQA-2018 is the BEIR benchmark's financial-domain QA task. The sampler pulls
  it through `ir_datasets` (`beir/fiqa/test`), which mirrors the original task
  data for academic use.
- DuReader-retrieval is the Baidu Research passage-retrieval benchmark from
  arXiv:2203.10232. The sampler pulls the `zyznull/dureader-retrieval-ranking`
  HuggingFace mirror of the official data; the original distribution is
  maintained by Baidu at
  <https://github.com/baidu/DuReader/tree/master/DuReader-Retrieval>.
- CmedqaRetrieval is a C-MTEB Chinese medical-QA retrieval task. The sampler
  pulls the `C-MTEB/CmedqaRetrieval` corpus/queries and
  `C-MTEB/CmedqaRetrieval-qrels` relevance judgments, both HuggingFace mirrors
  for academic use.

Generated dataset samples, sweep outputs, and the local retrieval suite/manifest
are also gitignored. They can be regenerated with the commands in this runbook
and do not need to be managed in version control.

## Ingestion and labeling

Each Source is ingested as a real text file and processed by the normal worker:

```sh
go run ./cmd/rag-eval ingest-samples \
  -samples evals/rag/.dataset-cache/msmarco-passage-v1.jsonl \
  -manifest-out evals/rag/.dataset-cache/sources-msmarco.json \
  -database-url 'postgres://nano:nano@localhost:55432/nano?sslmode=disable' \
  -user-id <user> -notebook-id <notebook> -index-version-id <version>
```

The product quota is 50 Sources per Notebook. With the default counts (120
MS MARCO + 40 FiQA + 40 English distractors, and the Chinese equivalents; see
`--msmarco-count`/`--fiqa-count`/`--dureader-count`/`--cmedqa-count`/
`--distractor-count` on `prepare_dataset.py`), each language now needs several
Notebooks, not just one. Run `ingest-samples` once per sub-dataset file (or a
pre-split shard of one) with its own `-notebook-id`, keeping every invocation
under 50 rows; the combined manifest records per-case `user_id` and
`notebook_id` overrides so `build-suite` can resolve them uniformly afterward.

`rag-eval build-suite` resolves active Evidence Revisions and writes all Units of
each official relevant passage as the expected set:

```sh
go run ./cmd/rag-eval build-suite \
  -samples evals/rag/.dataset-cache/samples-combined.jsonl \
  -manifest evals/rag/.dataset-cache/sources-combined.json \
  -manifest-out evals/rag/retrieval-sweep-sources-v1.json \
  -database-url 'postgres://nano:nano@localhost:55432/nano?sslmode=disable' \
  -index-version-id <version> \
  -out evals/rag/retrieval-sweep-v1.json
```

Use `rag-eval units` to preview the actual Unit IDs and text before labeling:

```sh
go run ./cmd/rag-eval units \
  -manifest evals/rag/retrieval-sweep-sources-v1.json \
  -database-url 'postgres://nano:nano@localhost:55432/nano?sslmode=disable'
```

## Sweep

```sh
go run ./cmd/rag-eval sweep \
  -suite evals/rag/retrieval-sweep-v1.json \
  -grid evals/rag/retrieval-sweep-grid-v1.json \
  -manifest evals/rag/retrieval-sweep-sources-v1.json \
  -out-prefix evals/rag/sweep-out/retrieval-sweep-v1 \
  -database-url 'postgres://nano:nano@localhost:55432/nano?sslmode=disable' \
  -qdrant-url http://127.0.0.1:56333 \
  -qdrant-collection nano-source-evidence-gemini-2-768-v1 \
  -bifrost-url http://127.0.0.1:56666
```

Output:

- `<prefix>.json`: full case-level report with stage diagnostics.
- `<prefix>.csv`: one row per parameter combination with aggregate Recall, MRR,
  completed/failed cases, and mean stage milliseconds.

Quick summary:

```sh
python3 scripts/rag-eval/summarize_sweep.py \
  evals/rag/sweep-out/retrieval-sweep-v1.json
```

The default grid is the confirmed 81-combination cross product around the
production baseline 40/40/60/20:

- `dense_candidates`: 20, 40, 80
- `sparse_candidates`: 20, 40, 80
- `rrf_k`: 30, 60, 100
- `rerank_candidates`: 10, 20, 40

## Results

Full 81-combination run completed with 8,100 case searches and 0 failures.
Report files:

- `evals/rag/sweep-out/retrieval-sweep-v1.json`
- `evals/rag/sweep-out/retrieval-sweep-v1.csv`

### Quality

| Metric | Result |
| --- | --- |
| Grid combinations | 81 |
| Case searches | 8,100 |
| Failed searches | 0 |
| Recall range | 1.000 across all combinations |
| MRR range | 0.9825 across all combinations |

Every query is paired with exactly one relevant passage, and the sweep pins only
50 Sources per Notebook. Retrieval therefore always finds the expected Unit, so
this first suite cannot discriminate between `top_k`, `rrf_k`, or
`rerank_candidates` on Recall/MRR. It does provide honest latency data and shows
that the pipeline is reliable on the current production Index Version.

### Latency

The baseline production configuration `40/40/60/20`:

| Stage | Mean |
| --- | --- |
| Dense | 1.08 ms |
| BM25 | 1.02 ms |
| Fuse | 0.01 ms |
| Evidence load | 3.79 ms |
| Rerank | 0.25 ms |
| Total | 6.15 ms |

Latency range across the grid:

| Metric | Fastest | Slowest |
| --- | --- | --- |
| Total mean | 6.01 ms | 23.88 ms |

Fastest observed combination: `dense=20, sparse=80, rrf_k=30,
rerank=20`. Slowest observed combination: `dense=20, sparse=20, rrf_k=30,
rerank=10`. Most of the spread comes from dense/BM25/evidence-load timing rather
than rerank.

### Interpretation

This run proves the retrieval-layer sweep tooling end to end, but the dataset
above is too easy for parameter tuning: every query is paired with exactly one
relevant passage and the sweep pinned only 50 Sources per Notebook, so the
expected Unit was essentially always found.

The dataset and tooling gaps that caused this are now closed:
`prepare_dataset.py` adds random distractor passages per sub-dataset and two
additional verticals (see "Data" above), and `RetrievalCaseResult` in
`internal/rageval/retrieval_eval.go` now reports each returned candidate's
`rerank_score` and whether it matched the expected Unit
(`candidate_scores` in the sweep JSON report), so a real score distribution for
relevant vs. irrelevant candidates can finally be read off a sweep run.

What's still open is running it: this section's numbers have not been
regenerated against the extended suite yet. That rerun, plus picking
`rerank_relevance_threshold` from the resulting score separation and setting it
in `evals/rag/pinned-config-v1.json`, is the remaining step in
`docs/superpowers/specs/2026-08-05-rerank-relevance-gate-design.md`.

## Operational notes

- Query embeddings are cached per case, reducing the full sweep from 8,100
  embedding calls to 100. Rerank is not cached because the candidate set changes
  with each grid row.
- Every active Notebook Run is refreshed before each search so a long sweep does
  not expire `agent_jobs.lease_expires_at` or `agent_runs.deadline_at`.
- The Gemini embedding free tier previously returned `429 RESOURCE_EXHAUSTED`
  with limit `embed_content_free_tier_requests: 1000`. A paid tier or a later
  quota reset is required if a sweep without embedding caching is repeated.
